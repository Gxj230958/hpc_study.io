# Benchmark：先明确你在比较什么

Benchmark 是按明确规则运行的性能测试。它帮助比较系统，也容易被误用。本章目标是写出一份别人能够复查的测量报告。

## 先正确，再计时

两个程序必须完成相同任务，达到相同精度要求，才适合比较。少算一部分数据、放宽误差或跳过验证，不能直接算作加速。并行代码尤其需要独立的参考结果。

记录硬件、软件版本、输入、线程数和计时范围。分清初始化、数据读取、主机设备传输、kernel 和结果写回。GPU 默认异步执行，主机计时必须在结束点等待设备完成，或使用正确放置的 CUDA event。

## 一个简单的测量协议

1. 先用小输入检查正确性。
2. 固定输入与线程数，运行几次预热。
3. 至少重复五次，保留全部结果。
4. 报告中位数和波动范围，不只挑最快值。
5. 一次只改变一个主要因素，避免多个实验争抢资源。

仓库 CUDA 示例输出的是驻留设备输入的 kernel 计时，以及首次输入传输、kernel、输出传输的时间。首次路径可能有冷启动影响，不能把两列直接相减得出稳定传输成本。

## 加速比与扩展性

加速比是 `S(p)=T(1)/T(p)`，效率是 `E(p)=S(p)/p`。强扩展固定总问题规模，增加工作者。弱扩展让每个工作者的任务规模近似不变，总任务随工作者增长。

若串行部分占 20%，即使其余部分无限快，理想总加速也不超过 5 倍。这是 Amdahl 模型给出的上限，不是每次运行都必须达到的结果。

## 综合实验（约 2 小时）

用 [OpenMP 求和](../parallel-programming/openmp.md)制作一张原始记录表。分别改变线程数与输入大小，计算加速比。写出哪些数据支持结论，哪些可能受缓存或 CPU 配额影响。

练习：程序 A 用 FP64，程序 B 用 FP16，只比较秒数是否公平？

??? success "参考答案"
    不充分。需要先明确应用允许的误差，并分别验证两者。若精度要求不同，应明确报告为不同配置，不能把差异全部归因于实现优化。

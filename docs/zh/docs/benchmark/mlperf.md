# MLPerf：机器学习测试也有任务与规则

机器学习性能不能只看一次矩阵乘法。数据处理、模型结构、精度目标和请求模式都会影响结果。本节介绍如何阅读 MLPerf，而不是提交一个正式成绩。

## 训练与推理不同

训练需要更新模型参数，关注达到规定质量目标所用的时间。推理使用已有模型处理请求，可能关注吞吐量，也可能关注延迟限制。不同场景的指标不能混为一个“每秒多少次”。

例如离线批处理更关心大量输入的总吞吐量。在线服务还关心用户等待多久，以及较慢请求的尾部延迟。平均延迟低，不代表所有请求都快。

## 公平比较需要固定条件

检查模型、数据集、精度要求、场景、软件栈和功耗口径。正式运行还涉及版本、规定的负载生成、日志与合规要求。规则可能变化，运行前查看 [MLCommons 官方基准](https://mlcommons.org/benchmarks/)。

不能把随手写的 PyTorch 循环叫作 MLPerf 成绩，也不能省略质量验证只报更高吞吐量。

## 教学实验：先学测量方法

```bash
python examples/ml/train.py --device cpu
python examples/ml/train.py --device cuda
python examples/ml/precision.py
```

这些是小型合成回归和矩阵计算实验，不是 MLPerf。回归程序检查训练损失下降，精度实验比较 FP32 与 FP16 的误差和同步计时。它们帮助认识训练、推理算子、质量与时间的关系。

## 综合阅读练习

从官方结果中选择同一轮、同一任务和同一场景的两项成绩，列出硬件数量、质量约束和测量指标。只解释可确认的差异，不把不同规则下的数字直接排序。

练习：batch size 从 1 增到 128，吞吐量提高，能否断言在线用户体验改善？

??? success "参考答案"
    不能。凑齐批次可能增加排队等待，单请求延迟也可能变化。还要测目标负载下的延迟分布，并检查服务约束。

参考：[MLPerf Inference](https://github.com/mlcommons/inference)、[MLPerf Training](https://github.com/mlcommons/training)。

# 死锁：大家都在等别人

死锁是多个执行者互相等待，导致程序无法继续。本节学习最常见的 MPI 等待环，不需要复杂算法背景。

## 看似对称，实际危险

假设 rank 0 和 rank 1 都先执行阻塞发送，再执行接收。如果发送需要接收方先准备好，两边就会一直等。小消息可能因内部缓冲“碰巧能跑”，换成大消息后才暴露错误。

```text
rank 0: Send(to=1) -> Recv(from=1)
rank 1: Send(to=0) -> Recv(from=0)
```

这是一段错误协议示意，不提供可直接运行的挂死程序。排查时画出“谁等谁”的箭头，比反复增加 barrier 更有效。

## 三种修复思路

一边先发、另一边先收；使用 `Sendrecv` 表达成对交换；或先发布非阻塞接收，再发送，并等待请求完成。选择后仍需检查 rank、tag、通信器、数据类型和长度。

仓库中的 `examples/mpi/pingpong.py` 采用第一种方法：rank 0 先发后收，rank 1 先收后发。

```bash
timeout 30s mpiexec -n 2 python examples/mpi/pingpong.py
```

超时是定位问题的保护措施，不是正确性证明。若失败，先保留日志，再缩小到两个 rank 和最小消息。

## 集合通信也会等待

如果一部分进程先执行广播，另一部分先执行归约，调用顺序不匹配也可能挂住。只有 rank 0 进入一个全通信器集合调用同样不正确。

练习：在所有 Send 前面加 Barrier，能解决上面的等待环吗？

??? success "参考答案"
    不能。它只让大家更接近同时进入同一个错误协议。需要改变发送接收关系，而不是仅增加同步。

参考：[MPI 标准中的点对点通信](https://www.mpi-forum.org/docs/)。
